# V6 全新仓库静态冒烟测试协议

V6 使用一个从未出现在既有研究记录中的公开仓库，检查当前 Vertex Palace
开发候选版能否把历史修复任务路由到后来由上游实际修改的实现文件与聚焦测试。
这是单仓库探索证据，不是发布门槛，也不是性能研究。

## 目标冻结

1. 从 Vertex Palace 产品仓库与本测试仓库的所有 tracked 文件中提取 GitHub
   仓库身份，形成偏保守的完整排除表。
2. 查询 GitHub 最近更新、已合并并关联关闭 issue 的前 100 个 PR。
3. 机械保留公开、活跃、非 fork，主语言为 JavaScript、TypeScript、Python、
   Go 或 Rust 的仓库；PR 必须修改 2-8 个文件、不超过 500 行，并同时包含
   至少一个实现文件与一个测试文件。
4. 排除自动化、发布、纯文档、build、CI 与依赖更新 PR。
5. 以最小的 `SHA-256(seed + "\n" + PR URL)` 选择唯一目标。
6. 在任何目标级 Palace 调用前，冻结完整候选池摘要、随机种子、仓库、父提交、
   merge commit、任务文本、候选 CLI 哈希、公开 `0.4.0` npm shasum、上游
   diff 哈希与私有真值承诺。

目标公开后禁止替换。若任务语义不一致、仓库不可用或工具不支持，该问题本身
就是本轮结果。

## 静态执行

- 候选版与公开 `vertex-palace@0.4.0` 各运行两次，顺序执行并平衡先后顺序。
- 每次观察都从相同父提交的干净隔离 clone 开始，不预置 `.palace`。
- 完整 issue 文本已经冻结在本地，因此统一使用 `referencePolicy=off`。
- Palace 看不到上游 merge diff；diff 只用于形成实现、聚焦测试与附属真值。
- 完整 context 输出保存在忽略追踪的 `.benchmark-runs/`，提交的结果只保留
  测量值与路线文件，不保存本机 transcript。

## 描述性门槛

候选版两次调用都成功、路线与模式完全一致、context 不超过 6000 估算 Token、
不污染 tracked 文件、核心覆盖率至少 0.50、同时命中实现与聚焦测试、路线聚焦度
至少 0.40，才视为本次冒烟通过。

无论通过或失败，一个目标都不能证明普遍路由质量、节省 Token、提高速度或
Agent 修复正确率。
